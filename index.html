演员表 · 这个系统里的四种模型

全页读下来你会遇到四种模型，分工和身价完全不同。先认脸，后面出场就不慌：

模型出场干哪份活身价
大模型（生成模型）⑤⑦读资料、组织答案——系统里唯一「会写文章」的最贵最慢，按 token 收费，能省一次是一次
嵌入模型 BGE-M3③④翻译官：把一句话压成一串数字（向量），意思近的句子数字也排得近中等，本地部署随便跑、不花钱
重排模型 bge-reranker-large④判卷老师：把「问题 + 段落」放一起精读打分偏贵，只给少量决赛选手用
分类模型 BERT 小模型⑤门口护士：毫秒级分清「通用闲聊还是专业咨询」极快极便宜，几乎免费

一句话记牢：学霸答题（大模型）、翻译官变数字（嵌入）、判卷老师精读（重排）、护士分诊（分类）——从前往后一个比一个小、快、便宜。⑤⑥两章的省钱思路就是这条：能用便宜模型拦住的，绝不劳驾贵的。

场地 · 三种数据库各管什么

数据库出场存什么大白话
MySQL⑥⑦FAQ 问答对、每轮会话记录账本：正经记账，掉电不丢；但只会「按条件精确对账」
Redis⑥最高频 FAQ 的缓存便签墙：贴在最顺手的地方，来问的人对一眼就秒回；掉电就没了，所以只放热门
Milvus③④子块正文 + 两种向量向量书架：专管「意思相近」的查找——MySQL 的 Ctrl+F 干不了的活

新手最常见的疑问：「为什么不全都存 MySQL？」——MySQL 的 LIKE 查询是 Ctrl+F，字面一模一样才查得到：「怎么保养车」永远查不到「汽车维护技巧」。Milvus 吃的是向量，按意思远近找。三种库不是重复建设，是各管一种找法：精确对账（MySQL）、秒回高频（Redis）、意思相近（Milvus）。

大模型三常识

token：模型眼里的「字」。英文一个单词约 1~2 个 token，中文一个汉字约 1~1.5 个。大模型按 token 计费，也按 token 逐个往外吐——所以「逐 token 输出」就是「每写出一小截就立刻推给你」，第⑦章流式输出说的就是它。

温度（temperature）：发挥程度的旋钮，取值 0~2。越低越死板稳定（同一个问题每次答案几乎一样），越高越发散天马行空。本课在⑤章用了两次：选检索策略时 0.1（要稳，别乱选）、最终作答时 0.5（要自然，别死板）。

幻觉：模型一本正经地编。它不觉得自己在骗你——它只会「顺着话往下接」，接不出实话时就接一句像模像样的假话。RAG 整套系统存在的意义就是给它递资料：「照着资料答，资料不够就转人工」，从根上压幻觉。

读

文档加载

把各种格式的教材，统一誊抄成「馆藏卡片」

这一步在干嘛：按文件扩展名挑选对应的加载器（Loader），把 txt / pdf / docx / ppt / 图片 / md 全部读成统一的 Document 对象 —— 一段正文 + 一组元数据。

为什么要这一步：向量数据库不认识「PDF」也不认识「PPT」，它只收纯文本。不管原始资料长什么样，进库前必须先誊抄成标准格式。

大白话：图书馆收书

图书馆收书时，不管你送来的是精装书、活页夹还是一叠照片，管理员都会先誊抄成统一格式的馆藏卡片：正文一份，标签若干。这里的四个标签（元数据）是：

元数据大白话
source这本书属于哪个书架 —— 从目录名截取（ai_data → ai，即「人工智能」学科），后面可以只查某个学科
file_path原件放在哪里，答错了好溯源
file_type原件是什么材质，决定它当初用哪把「刀」来切
timestamp什么时候入的库，方便知道资料新旧

最容易踩的坑：扫描版 PDF 和照片没有文字层，普通加载器读出来是空的。所以这套代码里 pdf / docx / ppt / 图片全部走 OCR 系加载器 —— 先「看图识字」，再交出文本。

# 定义不同文档加载需要使用的加载器：扩展名 -> 加载器
document_loaders = {
    ".txt": TextLoader,                # 纯文本直接读
    ".pdf": OCRPDFLoader,              # PDF（含扫描件）：先 OCR 看图识字
    ".docx": OCRDOCLoader,             # Word
    ".ppt": OCRPPTLoader,              # PPT / PPTX
    ".pptx": OCRPPTLoader,
    ".jpg": OCRIMGLoader,              # 图片
    ".png": OCRIMGLoader,
    ".md": UnstructuredMarkdownLoader  # Markdown
}

def load_documents_from_directory(directory_path: str) -> [Document]:
    documents = []
    # 从目录名截取学科（来源），如 "ai_data" -> "ai"
    source = os.path.basename(directory_path).split('_')[0]
    # os.walk 递归遍历目录及其子目录下的所有文件
    for root, _, files in os.walk(directory_path):
        for filename in files:
            file_path = os.path.join(root, filename)
            file_type = os.path.splitext(filename)[1]
            # 不支持的类型：记日志后跳过，不让一个怪文件毁掉整批
            if file_type not in document_loaders:
                logger.info(f"{file_path}文件不支持加载")
                continue
            loader_class = document_loaders[file_type]
            # txt 需要显式指定编码，其余交给各加载器自己处理
            if file_type == ".txt":
                loader = loader_class(file_path, encoding="utf-8")
            else:
                loader = loader_class(file_path)
            docs = loader.load()
            for doc in docs:  # 给每个文档贴 4 个元数据标签
                doc.metadata["source"] = source                    # 学科来源
                doc.metadata["file_path"] = file_path              # 原始路径
                doc.metadata["file_type"] = file_type              # 文件类型
                doc.metadata["timestamp"] = datetime.now().isoformat()  # 时间戳
            documents.extend(docs)
    return documents

切

父子块拆分

用小块找，用大块答

这一步在干嘛：把每个文档先按粗粒度切成父块（比如一页、一章），再把每个父块按细粒度切成子块（比如一段）。子块会随身携带两个「寻亲信息」：parent_id 和 parent_content。

为什么要这一步：向量模型对小文本更敏感。一整章塞进去，主题一杂，向量就成了「平均模糊」的意思，查不准；但只把一小段丢给大模型，上下文又不够，答不好。于是用两层：子块小而聚焦，负责「被搜到」；父块大而完整，负责「被读懂」。

大白话：背课文

一整本书直接背是背不下来的。先把书按章背成大段（父块），每章再按知识点拆成小段（子块）。考试时：用小段去「对题」（准），对上之后背整章来组织答案（全）。查字典也一个道理 —— 查的是词条（子块），理解要看整段释义（父块）。

两把刀，各切各的

整套拆分其实只有两条互相独立的流水线，在入口处按文件类型分流，互不掺和：

刀法一 · 通用刀刀法二 · 标题刀
伺候谁txt / pdf / docx / ppt / 图片 OCR —— 日常主力只伺候 .md 文件
用什么刀ChineseRecursiveTextSplitterMarkdownTextSplitter
怎么下刀先试段落 → 再试句子 → 兜底按字符，认长度不认结构认 # 标题层级，尽量切在章节边界
切完之后流程完全相同：父块粗切 → 子块细切 → 子块带「寻亲三件套」

无论哪种刀法，CHUNK_OVERLAP（重叠区）都在起同样的作用：相邻两块带一点公共内容，防止一句话被拦腰切断 —— 谁也不缺胳膊少腿。

conf = Config()  # 读入 PARENT_CHUNK_SIZE / CHILD_CHUNK_SIZE / CHUNK_OVERLAP

def process_documents(documents: [Document]) -> [Document]:
    # 入口分流：md 走刀法二，其余全走刀法一 —— 两条线各自独立
    chunks = []
    for i, doc in enumerate(documents):
        if doc.metadata["file_type"] == ".md":
            chunks.extend(split_markdown(doc, i))   # ── 刀法二 · 标题刀
        else:
            chunks.extend(split_normal(doc, i))     # ── 刀法一 · 通用刀
    return chunks

# ══════ 刀法一 · 通用刀：txt / pdf / docx / ppt / 图片 OCR ══════
# 按段落 → 句子 → 字符的顺序递归下刀，认长度不认结构
def split_normal(doc, doc_index):
    return _split_parent_then_child(doc, doc_index,
        parent_splitter=ChineseRecursiveTextSplitter(
            chunk_size=conf.PARENT_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP),
        child_splitter=ChineseRecursiveTextSplitter(
            chunk_size=conf.CHILD_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP))

# ══════ 刀法二 · 标题刀：只伺候 Markdown ══════
# 认 # 标题层级，尽量切在章节边界，不会把两章缝在一块
def split_markdown(doc, doc_index):
    return _split_parent_then_child(doc, doc_index,
        parent_splitter=MarkdownTextSplitter(
            chunk_size=conf.PARENT_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP),
        child_splitter=MarkdownTextSplitter(
            chunk_size=conf.CHILD_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP))

# ══════ 两种刀法共用的「先父后子」两步流程 ══════
def _split_parent_then_child(doc, doc_index, parent_splitter, child_splitter):
    chunks = []
    # 第一步：粗切父块
    for j, parent_doc in enumerate(parent_splitter.split_documents([doc])):
        parent_doc_id = f"doc_{doc_index}_parent_{j}"
        # 第二步：细切子块
        for k, child_doc in enumerate(child_splitter.split_documents([parent_doc])):
            # 子块带三件套：自己的 id、父块 id、父块全文
            child_doc.metadata["id"] = f"{parent_doc_id}_child_{k}"
            child_doc.metadata["parent_id"] = parent_doc_id
            child_doc.metadata["parent_content"] = parent_doc.page_content
            chunks.append(child_doc)
    return chunks  # 父块不单独入库，它搭在子块的行李里

def process_documents(documents: [Document]) -> [Document]:
    chunks = []  # 最终只保存子块
    # 两把刀都先备好，走哪条线临时挑
    parent_splitter = ChineseRecursiveTextSplitter(
        chunk_size=conf.PARENT_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP)
    child_splitter = ChineseRecursiveTextSplitter(
        chunk_size=conf.CHILD_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP)
    md_parent_splitter = MarkdownTextSplitter(
        chunk_size=conf.PARENT_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP)
    md_child_splitter = MarkdownTextSplitter(
        chunk_size=conf.CHILD_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP)

    for i, doc in enumerate(documents):
        # md 用 Markdown 切分器，其余用中文递归切分器
        is_md = doc.metadata["file_type"] == ".md"
        parent_splitter_to_use = md_parent_splitter if is_md else parent_splitter
        child_splitter_to_use = md_child_splitter if is_md else child_splitter

        # 粗切父块 -> 细切子块 -> 子块带三件套，流程同上
        parent_docs = parent_splitter_to_use.split_documents([doc])
        for j, parent_doc in enumerate(parent_docs):
            parent_doc_id = f"doc_{i}_parent_{j}"
            child_docs = child_splitter_to_use.split_documents([parent_doc])
            for k, child_doc in enumerate(child_docs):
                child_doc.metadata["id"] = f"{parent_doc_id}_child_{k}"
                child_doc.metadata["parent_id"] = parent_doc_id
                child_doc.metadata["parent_content"] = parent_doc.page_content
                chunks.append(child_doc)

    return chunks  # 注意：父块不单独入库，它搭在子块的行李里
怎么验证这一步跑通了：运行后打印 chunks，检查三件事：① 子块数量明显多于文档数；② 每个 chunk.metadata["parent_id"] 形如 doc_0_parent_1；③ 同一父块切出的子块，parent_content 完全一致。再对比 PARENT_CHUNK_SIZE 与 CHILD_CHUNK_SIZE，父块平均长度应明显更大。
记住八个字：用小的找，用大的答。子块像书的目录词条，负责被精准搜到；父块像整页正文，负责给大模型足够的上下文。
为什么小块查得更准？一段话主题越单一，它的语义向量就越「立场鲜明」。一大章什么都讲，向量就被平均成一锅粥，跟哪个问题都有点像、又都不像。

向量化与入库

BGE-M3 一鱼两吃：稠密 + 稀疏，写进 Milvus

这一步在干嘛：拿本地部署的 BGE-M3 嵌入模型，把每个子块的文本同时转成两种向量 —— 稠密向量（1024 维的浮点数组）和稀疏向量（词 → 权重的字典），连同元数据一起写进 Milvus。

为什么要两种向量：它们是两套互补的「找书」本事。

大白话：印象派 vs 检字法

稠密向量：把整句话的「意思」压缩成 1024 个小数。意思近的句子，这串数字就排得近。查询「如何保养车辆」，它能找到一条词都不重合的「汽车维护技巧」—— 靠的是印象，认意思不认字面。

稀疏向量：先分词，每个词在词表里有个「座位号」，命中就记权重，其余上万个座位全是 0 —— 这就是「稀疏」二字的来历。查询里出现「保养」「车辆」，它就精确翻出含这两个词的段落 —— 靠的是检字，认字面不认意思。

教学场景术语多且容不得似是而非（「有理数」和「无理数」意思差十万八千里，稠密向量却觉得挺像），所以两路一起上，互相兜底。

实验台 · 双向量透视仪

一句话，两种向量化演示数据为教学模拟，真实数值由 BGE-M3 计算

稠密向量 dense · 1024 维 → 压缩展示 48 格

整句语义压成一条「印象指纹」，意思近 → 条纹长得像

稀疏向量 sparse · 词表座位号 → 权重

只有分出来的词有值，其余座位全为 0（条形码既视感）

看这张表的两个名场面：「汽车维护技巧」稠密高分 / 稀疏 0.00 —— 意思近、字面远，这是稠密的价值；「如何保养皮肤」稀疏高分 / 稠密 0.00 —— 两个词撞上了、意思差远了，这是稀疏的盲区。最后一列加权融合，就是第 4 步 WeightedRanker 的雏形。

上面就是这句子块最终在 Milvus 里占的一行：两种向量各占一列，父块信息随行李携带，MD5 当主键。

字段类型大白话
idVARCHAR 主键子块内容的 MD5 —— 内容不变，重复入库也只算一条

    def add_documents(self, documents: [Document]):
        texts = [doc.page_content for doc in documents]
        # 一次性批量向量化：BGE-M3 同时返回 dense 和 sparse
        embeddings = self.embedding(texts)

        data = []
        for i, doc in enumerate(documents):
            # 内容 MD5 作主键：同样内容重复入库 -> 覆盖而不是重复
            text_hash = hashlib.md5(doc.page_content.encode("utf-8")).hexdigest()
            # 稀疏向量在返回值里是压缩行格式，摊开成 {座位号: 权重}
            sparce_vector = {}
            row = embeddings['sparse'][[i]]
            for index, value in zip(row.indices, row.data):
                sparce_vector[index] = value
            data.append({
                "id": text_hash,
                "text": doc.page_content,
                "dense_vector": embeddings['dense'][i],
                "sparse_vector": sparce_vector,
                "parent_id": doc.metadata["parent_id"],
                "parent_content": doc.metadata["parent_content"],
                "source": doc.metadata.get("source", "unknown"),
                "timestamp": doc.metadata.get("timestamp", "unknown"),
            })
        if data:
            # upsert = 有则覆盖，无则插入；重建知识库时可放心重跑
            self.client.upsert(collection_name=conf.MILVUS_COLLECTION_NAME, data=data)
            logger.info(f"已插入或更新 {len(data)} 个文档")

稠密向量像印象派画家：看整体神韵，管它用词是否相同 —— 「如何保养车辆」和「汽车维护技巧」在它眼里是近亲。

MD5 主键 + upsert 的组合拳，让「重建知识库」变成可以随便重跑的操作 —— 内容没变就不产生重复数据。

检

混合检索与重排

两路召回 → 融合去重 → 精排取 Top-M

这一步在干嘛：用户的问题先用同一个 BGE-M3 转出稠密 + 稀疏两种向量；两路各查回 k 条，用 WeightedRanker 加权融合；按父块去重后，交给 bge-reranker-large 精排，只留 Top-M 个父块送进大模型。

为什么要这么绕：因为「快」和「准」是一对矛盾。向量检索是「各查各的、内积合分」，快，但粗；CrossEncoder 重排要把「问题 + 段落」成对塞进模型逐字精读，准，但慢。所以流程设计成漏斗：先用便宜的方法把几万条筛到几十条，再让昂贵的精读只看这几十条。

大白话：三关选拔

第一关 · 两路初筛：印象派（稠密）和检字法（稀疏）各自报出最像的 k 条候选。 第二关 · 加权合议：WeightedRanker(0.7, 1.0) 把两路分数加权求和 —— 注意顺序要跟 reqs=[sparse_request, dense_request] 对齐，0.7 给稀疏、1.0 给稠密，即更信语义，但字面命中也加分；写反了效果全变。同一个父块的多个子块都命中时，只留一份父块，免得大模型读到复读机内容。第三关 · 面试精排：reranker 把「问题和段落放在一起精读」打分 —— 它不像向量检索那样「各算各的再比」，而是看两者放在一起是否真的匹配，所以更能排除「词都对上、答非所问」的凑数选手。

    def hybrid_search_with_reranker(self, query, k=conf.RETRIEVAL_K, source_filter=None):
        # 1) 问题同样做双向量化 —— 必须用和入库时同一个模型
        embeddings = self.embedding([query])
        dense_query_vector = embeddings['dense'][0]
        sparse_query_vector = {}
        row = embeddings["sparse"][[0]]
        for idx, val in zip(row.indices, row.data):
            sparse_query_vector[idx] = val

        # 2) 组装两路搜索请求（可带 source 过滤：只在某个学科书架里找）
        filter_expr = f"source == '{source_filter}'" if source_filter else ""
        sparse_request = AnnSearchRequest(
            data=[sparse_query_vector], anns_field="sparse_vector",
            param={"metric_type": "IP", "params": {}},
            limit=k, expr=filter_expr)
        dense_request = AnnSearchRequest(
            data=[dense_query_vector], anns_field="dense_vector",
            param={"metric_type": "IP", "params": {"nprobe": 10}},
            limit=k, expr=filter_expr)

        # 3) 加权融合：reqs 顺序是 [稀疏, 稠密]，
        #    所以 0.7 给稀疏、1.0 给稠密 —— 更信语义，字面命中也加分
        ranker = WeightedRanker(0.7, 1.0)
        results = self.client.hybrid_search(
            collection_name=conf.MILVUS_COLLECTION_NAME,
            reqs=[sparse_request, dense_request],
            ranker=ranker, limit=k,
            output_fields=["text", "parent_id", "parent_content",
                           "source", "timestamp"])[0]

        # 4) 命中的是子块，按父块内容去重，换回完整父块
        chunks = [self.__doc_from_hit(hit['entity']) for hit in results]
        parent_docs = self.__get_unique_parent_docs(chunks)
        if len(parent_docs) < 2:
            return parent_docs

        # 5) 少量候选交给 CrossEncoder 精读打分，取 Top-M
        pairs = [[query, doc.page_content] for doc in parent_docs]
        scores = self.reranker.predict(pairs)
        ranked = [doc for _, doc in sorted(zip(scores, parent_docs), reverse=True)]
        return ranked[:conf.CANDIDATE_M]

    def __doc_from_hit(self, hit):
        return Document(page_content=hit.get("text"), metadata={
            "parent_id": hit.get("parent_id"),
            "parent_content": hit.get("parent_content"),
            "source": hit.get("source"),
            "timestamp": hit.get("timestamp")})

    def __get_unique_parent_docs(self, chunks):
        parent_contents, unique_docs = set(), []
        for chunk in chunks:
            parent_content = chunk.metadata.get("parent_content")
            if parent_content and parent_content not in parent_contents:
                unique_docs.append(Document(page_content=parent_content,
                                            metadata=chunk.metadata))
                parent_contents.add(parent_content)
        return unique_docs

大白话：医院分诊台

进医院先过护士分诊：感冒发烧（通用知识）直接去普通门诊；专科问题（专业知识）才挂号进专科诊室，而且先翻你的病历（检索资料），医生看完病历再开口（大模型照资料作答）。分诊的是便宜的小护士（BERT 小模型，毫秒级），看病的是贵的大专家（大模型）—— 让专家只干专家该干的事。

三种检索策略，大白话各一句

直接检索：问法直白（「学费是多少」）就拿原话去查。假设问题检索（HyDE）：问得太抽象（「AI 在教育领域的应用」），向量库里没有一句话跟它「长得像」—— 先让大模型猜一个假设答案，拿这个答案去查。妙处在于：答案和文档说的是同一件事、用词相近，比抽象的问题好匹配。子查询检索：复合问题（「比较 Java 和 Python」）一次查不完整 —— 先拆成几个小问题分别查，结果去重合并。

两个细节值得记：策略选择时 temperature=0.1（要答案稳定，别发挥），最终回答时 0.5（要自然流畅）；策略选择失败的兜底是「直接检索」—— 系统任何一环出错都要有退路，不能卡死用户。

缓

缓存加速

常见问题根本不该进 RAG —— Redis 与 BM25 三级漏斗

这一步在干嘛：系统跑一段时间后会攒下常见问题（FAQ）。把它们和答案存进 MySQL，热门的再放 Redis。新问题来了先走两级快速通道：① Redis 精确命中直接秒回；② 没命中，用 BM25 算法和 MySQL 里的历史问题算相关度，最高分 ≥ 0.9 就直接返回那条答案；③ 都不行才进前面学的 RAG 全流程。

为什么要这一步：在线系统 80% 的流量往往是 20% 的常见问题。这些问题的答案早就有了，再跑一遍「向量检索 + 重排 + 大模型」纯烧钱。漏斗思想再次登场：便宜的挡在前面，贵的只在真正需要时出场。

大白话：客服的三本册子

便利贴墙（Redis）：最高频的问题答案直接贴墙上，来一个人对一眼，秒回。FAQ 手册（MySQL + BM25）：墙上的便签不全，但有一本按关键词索引的手册 —— 来的问题跟手册里某条「几乎一样」，翻出来照着念。全院会诊（RAG）：便签墙和手册都解决不了，才走完整流程：查资料库 → 精排 → 让专家现场作答。

BM25 大白话：会打分的关键词匹配

BM25 是「Ctrl+F 搜索的聪明版」：把问题和历史问题都分词，按关键词重合打分，但带三条常识修正 —— ① 查询词在某文档里出现得越多，该文档分越高；② 但一个全库到处都有的词（的、是、什么）几乎不加分类（IDF 折扣）；③ 文档越长越吃亏（长文档容易「碰巧」包含关键词，要稀释）。查询和「关联子查询的执行顺序是什么」几乎逐词重合的文档，分数自然鹤立鸡群。

分数还要过一遍 softmax 归一化：把一把参差不齐的分数压成「总和为 1 的百分比」，这才好定 0.9 的阈值 —— 意思是「最高票的文档要有九成把握才算命中」。定这么高是产品决策：FAQ 答错比答不出来更伤人，宁可放去走 RAG，也不把相近问题的答案张冠李戴。

def query(self, query, source_filter=None, session_id=None):
    answer = self.bm25_search.search(query, threshold=0.9)
    if answer:                                     # FAQ 命中：整段返回
        self.mysql_client.update_session_history(session_id, query, answer)
        yield answer, True
    else:                                          # RAG：逐 token 流出
        history = self.mysql_client.fetch_recent_history(session_id)
        collected = ""
        for token in self.rag_system.generate_answer(query, source_filter, history):
            collected += token
            yield token, False
        self.mysql_client.update_session_history(session_id, query, collected)
        yield "", True

这一步在干嘛：前面几章是一条写死的流水线（链，Chain）。LangGraph 把编排升级成图：节点是步骤（函数），边是走向（可带条件），状态在各节点间传递 —— 支持循环、分支、并行、人工介入，这正是复杂智能体需要的。

生态位是什么开源/商业

Chain 什么时候不够用？大白话：链是流水线传送带，图是地铁线路图 —— 地铁能环线（循环）、能换乘（分支）、能多线同发（并行）、能临时停车（人工介入）。比如烧水：水没开就回去接着烧 —— 传送带掉不了头，地铁图随便绕。

三件套：State / Node / Edge

State 状态：所有节点共享的一块黑板（TypedDict 类——Python 的「字典模板」，规定黑板上只能有哪几个字段、各是什么类型，字段名写错编辑器直接红线提醒），节点往黑板上写字，下一个节点接着读。Node 节点：一个函数，State 进、State 出。Edge 边：普通边 = 固定下一站；条件边 = 一个函数看黑板上的状态返回路由标识，查路由表决定下一站。

入门计算图x=x+y → x=x*y 的最小完整图
from typing import TypedDict
from langgraph.constants import START, END
from langgraph.graph import StateGraph

# 1) 状态：黑板，继承 TypedDict
class CalState(TypedDict):
    x: int
    y: int

# 2) 节点：State 进，State 出
def add_node(s: CalState) -> CalState:
    s["x"] = s["x"] + s["y"];  return s

def multi_node(s: CalState) -> CalState:
    s["x"] = s["x"] * s["y"];  return s

# 3) 建图：创建 → 加节点 → 加边 → 编译
g = StateGraph(CalState)
g.add_node("add_node", add_node)
g.add_node("multi_node", multi_node)
g.add_edge(START, "add_node")            # 普通边
g.add_edge("add_node", "multi_node")
g.add_edge("multi_node", END)
graph = g.compile()

graph.invoke({"x": 1, "y": 2})   # → {'x': 6, 'y': 2}

分支（条件边选路）：水温到 100 走「冲咖啡」，没到走「继续加热」。循环（条件边指回自己）：LangGraph 里没有 while —— 循环 = 「水没开 → 烧水节点自己」这条边，每次 +10 度直到 100。并行（START 同时连多个节点）：烧水和磨咖啡豆互不干扰同时干；都写同一个字段会打架，冲突字段要配合并规则 Annotated[int, rule]——读作「这个字段是 int，但并行多人同时写它时，按 rule 定的规矩合并（比如各加各的）」。人工介入（interrupt）：「先生要加糖吗？」—— 节点里调 interrupt() 整个图暂停，人通过 Command(resume="是") 喂回决策再继续；图必须带记忆，否则恢复不了。子图：烧水、加糖各自封装成小图再挂进总图，像函数封装一样治复杂性。

import fitz  # PyMuPDF（pip install PyMuPDF，别装成老的 fitz 包）
from langchain_core.documents import Document
from langchain_community.document_loaders.base import BaseLoader

class OCRPDFLoader(BaseLoader):
    """逐页处理：有文字层就抽文本；有图请 VLM 看图说话，解说词钉回原文"""
    def __init__(self, file_path: str):
        self.file_path = file_path

    def load(self) -> [Document]:
        docs, pdf = [], fitz.open(self.file_path)
        for page in pdf:
            text = page.get_text()                  # ① 有文字层：免费、一字不差
            for i, img in enumerate(page.get_images(full=True)):  # ② 有图才花钱
                pix = fitz.Pixmap(pdf, img[0])      # 抠出图片对象
                if pix.n - pix.alpha > 3:           # CMYK 等转 RGB
                    pix = fitz.Pixmap(fitz.csRGB, pix)
                caption = describe_image(pix.tobytes("png"))   # ③ 看图说话
                text += f"\n【图{i + 1}：{caption}】"           # ④ 钉回原文
            # 扫描版整页一张图：get_text() 为空，整页由 VLM 转述
            docs.append(Document(page_content=text,
                                 metadata={"page": page.number + 1}))
        pdf.close()
        return docs

def describe_image(img_bytes) -> str:
    """看图说话：任何 OpenAI 兼容接口都行（本地 Ollama / vLLM 或云端）。
    换模型只改 base_url 和 model，「读」之后的管线一行不改"""
    import base64
    from openai import OpenAI
    client = OpenAI(base_url="http://127.0.0.1:11434/v1", api_key="ollama")
    b64 = base64.b64encode(img_bytes).decode()
    resp = client.chat.completions.create(
        model="qwen2.5vl:7b",
        messages=[{"role": "user", "content": [
            {"type": "text", "text":
             "用中文详细描述这张图：图表请转写关键数据，"
             "流程图请列出步骤，公式请输出 LaTeX。"},
            {"type": "image_url",
             "image_url": {"url": f"data:image/png;base64,{b64}"}},
        ]}])
    return resp.choices[0].message.content.strip()

def load_documents_from_directory(directory_path: str) -> [Document]:
    """① 读：目录扫一遍，所有格式誊抄成统一格式的 Document + 4 个元数据章"""
    documents = []
    source = os.path.basename(directory_path).split('_')[0]  # ai_data -> ai
    for root, _, files in os.walk(directory_path):
        for filename in files:
            file_path = os.path.join(root, filename)
            file_type = os.path.splitext(filename)[1]
            if file_type not in document_loaders:      # 不支持的类型：记日志后跳过
                logger.info(f"{file_path}文件不支持加载")
                continue
            loader_class = document_loaders[file_type]
            # txt 显式指定 utf-8，其余交给加载器自己处理
            if file_type == ".txt":
                loader = loader_class(file_path, encoding="utf-8")
            else:
                loader = loader_class(file_path)
            for doc in loader.load():
                doc.metadata["source"] = source
                doc.metadata["file_path"] = file_path
                doc.metadata["file_type"] = file_type
                doc.metadata["timestamp"] = datetime.now().isoformat()
                documents.append(doc)
    return documents

def process_documents(documents: [Document]) -> [Document]:
    """② 切：入口分流 —— md 走标题刀，其余走通用刀，两条线互不掺和"""
    chunks = []
    for i, doc in enumerate(documents):
        splitter = split_markdown if doc.metadata["file_type"] == ".md" else split_normal
        chunks.extend(splitter(doc, i))
    return chunks

def split_normal(doc, doc_index):
    """刀法一 · 通用刀：段落 → 句子 → 字符递归下刀，认长度不认结构"""
    return _split_parent_then_child(doc, doc_index,
        parent_splitter=ChineseRecursiveTextSplitter(
            chunk_size=conf.PARENT_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP),
        child_splitter=ChineseRecursiveTextSplitter(
            chunk_size=conf.CHILD_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP))

def split_markdown(doc, doc_index):
    """刀法二 · 标题刀：认 # 标题层级，尽量切在章节边界"""
    return _split_parent_then_child(doc, doc_index,
        parent_splitter=MarkdownTextSplitter(
            chunk_size=conf.PARENT_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP),
        child_splitter=MarkdownTextSplitter(
            chunk_size=conf.CHILD_CHUNK_SIZE, chunk_overlap=conf.CHUNK_OVERLAP))

def _split_parent_then_child(doc, doc_index, parent_splitter, child_splitter):
    """两种刀法共用的「先父后子」：粗切父块 → 细切子块 → 子块带三件套"""
    chunks = []
    for j, parent_doc in enumerate(parent_splitter.split_documents([doc])):
        parent_doc_id = f"doc_{doc_index}_parent_{j}"
        for k, child_doc in enumerate(child_splitter.split_documents([parent_doc])):
            child_doc.metadata["id"] = f"{parent_doc_id}_child_{k}"
            child_doc.metadata["parent_id"] = parent_doc_id
            child_doc.metadata["parent_content"] = parent_doc.page_content
            chunks.append(child_doc)   # 父块不单独入库，搭在子块行李里
    return chunks

import hashlib
from langchain_core.documents import Document
from milvus_model.hybrid import BGEM3EmbeddingFunction
from pymilvus import MilvusClient, DataType, AnnSearchRequest, WeightedRanker
from sentence_transformers import CrossEncoder
from base.config import Config
from base.logger import logger

conf = Config()

class VectorStore:
    def __init__(self):
        # 1) BGE-M3：一个模型同时管稠密和稀疏（cuda → mps → cpu 择优）
        import torch
        device = ('cuda' if torch.cuda.is_available()
                  else 'mps' if hasattr(torch.backends, 'mps')
                       and torch.backends.mps.is_available()
                  else 'cpu')
        self.embedding = BGEM3EmbeddingFunction(
            model_name_or_path=conf.BGE_M3_MODEL_PATH,
            use_fp16=True, device=device)

        # 2) 连接 Milvus
        self.client = MilvusClient(
            uri=f"http://{conf.MILVUS_HOST}:{conf.MILVUS_PORT}",
            db_name=conf.MILVUS_DATABASE_NAME)

        # 3) 建表：8 个字段 + 两个索引（表已存在则跳过）
        if not self.client.has_collection(conf.MILVUS_COLLECTION_NAME):
            schema = self.client.create_schema(auto_id=False,
                                               enable_dynamic_field=True)
            schema.add_field("id", DataType.VARCHAR, is_primary=True, max_length=100)
            schema.add_field("text", DataType.VARCHAR, max_length=65535)
            schema.add_field("dense_vector", DataType.FLOAT_VECTOR,
                             dim=self.embedding.dim['dense'])    # 1024 维
            schema.add_field("sparse_vector", DataType.SPARSE_FLOAT_VECTOR)
            schema.add_field("parent_id", DataType.VARCHAR, max_length=100)
            schema.add_field("parent_content", DataType.VARCHAR, max_length=65535)
            schema.add_field("source", DataType.VARCHAR, max_length=50)
            schema.add_field("timestamp", DataType.VARCHAR, max_length=50)

            index_params = self.client.prepare_index_params()
            # 稠密：IVF_FLAT，128 个聚类「书架」，内积度量
            index_params.add_index(field_name="dense_vector", index_name="dense_index",
                index_type="IVF_FLAT", metric_type="IP", params={"nlist": 128})
            # 稀疏：倒排目录，构建时丢弃 20% 权重最小的词条换速度
            index_params.add_index(field_name="sparse_vector", index_name="sparse_index",
                index_type="SPARSE_INVERTED_INDEX", metric_type="IP",
                params={"drop_ratio_build": 0.2})
            self.client.create_collection(conf.MILVUS_COLLECTION_NAME,
                                          schema=schema, index_params=index_params)
            logger.info(f"已创建集合 {conf.MILVUS_COLLECTION_NAME}")

        # 4) 重排模型：CrossEncoder，把（问题, 段落）成对精读打分
        self.reranker = CrossEncoder(conf.RERANKER_MODEL_PATH)

    def add_documents(self, documents: [Document]):
        """③ 存：只有子块正文向量化；父块全文搭行李，不转向量"""
        texts = [doc.page_content for doc in documents]
        embeddings = self.embedding(texts)            # dense + sparse 一次全出
        data = []
        for i, doc in enumerate(documents):
            # 内容 MD5 当主键：重复入库只覆盖，不产生重复数据
            text_hash = hashlib.md5(doc.page_content.encode("utf-8")).hexdigest()
            sparse_vector = {}   # 压缩行格式摊开成 {座位号: 权重}
            row = embeddings['sparse'][[i]]
            for index, value in zip(row.indices, row.data):
                sparse_vector[index] = value
            data.append({
                "id": text_hash,
                "text": doc.page_content,
                "dense_vector": embeddings['dense'][i],
                "sparse_vector": sparse_vector,
                "parent_id": doc.metadata["parent_id"],
                "parent_content": doc.metadata["parent_content"],
                "source": doc.metadata.get("source", "unknown"),
                "timestamp": doc.metadata.get("timestamp", "unknown"),
            })
        if data:
            self.client.upsert(conf.MILVUS_COLLECTION_NAME, data=data)
            logger.info(f"已插入或更新 {len(data)} 个文档")

    def hybrid_search_with_reranker(self, query, k=conf.RETRIEVAL_K, source_filter=None):
        """④ 检：双向量化 → 两路召回 → 加权融合 → 父块去重 → 精排 Top-M"""
        # 1) 问题用同一个模型双向量化
        embeddings = self.embedding([query])
        dense_query_vector = embeddings['dense'][0]
        sparse_query_vector = {}
        row = embeddings["sparse"][[0]]
        for idx, val in zip(row.indices, row.data):
            sparse_query_vector[idx] = val

        # 2) 组装两路搜索（可带 source 过滤：只在某学科书架里找）
        filter_expr = f"source == '{source_filter}'" if source_filter else ""
        sparse_request = AnnSearchRequest(
            data=[sparse_query_vector], anns_field="sparse_vector",
            param={"metric_type": "IP", "params": {}},
            limit=k, expr=filter_expr)
        dense_request = AnnSearchRequest(
            data=[dense_query_vector], anns_field="dense_vector",
            param={"metric_type": "IP", "params": {"nprobe": 10}},
            limit=k, expr=filter_expr)

        # 3) 加权融合。权重顺序 = reqs 顺序：0.7 给稀疏、1.0 给稠密
        ranker = WeightedRanker(0.7, 1.0)
        results = self.client.hybrid_search(
            collection_name=conf.MILVUS_COLLECTION_NAME,
            reqs=[sparse_request, dense_request], ranker=ranker, limit=k,
            output_fields=["text", "parent_id", "parent_content",
                           "source", "timestamp"])[0]

        # 4) 命中的是子块，按父块去重换回完整父块
        chunks = [self.__doc_from_hit(hit['entity']) for hit in results]
        parent_docs = self.__get_unique_parent_docs(chunks)
        if len(parent_docs) < 2:
            return parent_docs

        # 5) 少量候选交给 CrossEncoder 精读打分，取 Top-M
        pairs = [[query, doc.page_content] for doc in parent_docs]
        scores = self.reranker.predict(pairs)
        ranked = [doc for _, doc in sorted(zip(scores, parent_docs), reverse=True)]
        return ranked[:conf.CANDIDATE_M]

    def __doc_from_hit(self, hit):
        return Document(page_content=hit.get("text"), metadata={
            "parent_id": hit.get("parent_id"),
            "parent_content": hit.get("parent_content"),
            "source": hit.get("source"),
            "timestamp": hit.get("timestamp")})

    def __get_unique_parent_docs(self, chunks):
        parent_contents, unique_docs = set(), []
        for chunk in chunks:
            parent_content = chunk.metadata.get("parent_content")
            if parent_content and parent_content not in parent_contents:
                unique_docs.append(Document(page_content=parent_content,
                                            metadata=chunk.metadata))
                parent_contents.add(parent_content)
        return unique_docs

import torch
from transformers import BertTokenizer, BertForSequenceClassification

class QueryClassifier:
    def __init__(self, model_dir):
        if not os.path.exists(model_dir):
            raise FileNotFoundError(f"模型目录不存在: {model_dir}")
        self.device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
        self.tokenizer = BertTokenizer.from_pretrained(model_dir)          # 分词器
        self.model = BertForSequenceClassification.from_pretrained(model_dir)
        self.model.to(self.device)
        self.model.eval()   # 评估模式：关掉 dropout，输出稳定

    def predict_category(self, query):
        if not query or not isinstance(query, str):
            return "通用知识"                     # 任何异常输入都兜底为通用
        try:
            encoding = self.tokenizer(query, truncation=True, padding=True,
                                      max_length=128, return_tensors="pt")
            encoding = {k: v.to(self.device) for k, v in encoding.items()}
            with torch.no_grad():                 # 推理不需要梯度
                outputs = self.model(**encoding)
                prediction = torch.argmax(outputs.logits, dim=1).item()
            return "专业咨询" if prediction == 1 else "通用知识"
        except Exception:
            return "通用知识"                     # 出错也兜底，绝不卡死用户

class BM25Search:
    def __init__(self):
        self.redis_client = RedisClient()
        self.mysql_client = MySQLClient()
        # 启动时从 MySQL 拉全部 FAQ 问题，分词后建 BM25 索引
        self.original_questions = self.mysql_client.fetch_questions()
        if not self.original_questions:
            logger.warning("未加载到问题")
            return
        tokenized = [jieba.lcut(q[0]) for q in self.original_questions]
        self.bm25 = BM25Okapi(tokenized)

    def search(self, query, threshold=0.9):
        # ① Redis：一模一样的问题，秒回
        cached = self.redis_client.get_answer(query)
        if cached:
            return cached

        # ② BM25：和 FAQ 手册里的问题算相关度，softmax 后过阈值
        scores = self.bm25.get_scores(jieba.lcut(query))
        softmax_scores = self._softmax(scores)
        best_idx = softmax_scores.argmax()
        if softmax_scores[best_idx] >= threshold:
            original_question = self.original_questions[best_idx]
            answer = self.mysql_client.fetch_answer(original_question)
            if answer:
                self.redis_client.set_data(f"answer:{query}", answer)  # 写回缓存
                return answer

        # ③ 都没接住 → 返回 None，主流程会转 RAG（第④⑤步）
        return None

快问快答

为什么用子块查询，却把父块送给大模型？
子块小、主题单一，语义向量「立场鲜明」，跟问题一比就分得出远近 —— 查得准。但只把一小段塞给大模型，它看到的上下文太少，容易答得干瘪或断章取义。父块大而完整，正好当答案的「课文原文」。所以：检索的精度靠子块，回答的质量靠父块。
稠密、稀疏各留一路不行吗？为什么要两个都要？
各有盲区：只用稠密，专业术语容易被似是而非的近义内容顶掉（「有理数」≈「无理数」）；只用稀疏，用户换个说法（「保养」说成「维护」）就查空。两路加权互补，一路失手另一路兜底 —— 这就是「混合检索」。
向量检索已经打了分，为什么还要 reranker 再打一次？
因为两路分数是「各算各的再合并」：问题和文档各自编码成向量后比内积，模型根本没见过它们放在一起的样子。CrossEncoder 把「问题， 段落」成对送进模型精读，直接判断「这段能不能回答这个问题」，准得多 —— 只是慢，所以只对去重后的少量父块用。
MD5 当主键，两块内容一样会怎样？万一不同内容撞了 MD5 呢？
内容一样 → id 一样 → upsert 覆盖，库里永远只有一条，这正是想要的幂等性。不同内容撞 MD5 的概率约 2^-128，工程上可以忽略；真要较真可以改成「MD5 + 文件路径」拼接。
重排之后取的是 Top-M 个父块，然后呢？
那就是下一课「生成」的入口了：把 Top-M 个父块作为参考资料模板化地拼进提示词（「请根据以下资料回答……」），连同用户问题一起发给大模型。本课的存储与检索，就是给这一步备料的。
检索返回了资料，大模型就一定答对吗？
不一定。检索只是「找到可能相关的原文」：资料找错了、或找对了但大模型没照着读，都会翻车。所以工程上要同时看两段指标 —— 检索准不准（命中率、排序质量）和生成好不好（是否忠于资料）。这也是为什么本课每个实验台都让你亲眼看分数和排序，而不是只看最终答案。
分诊为什么用自己训练的小 BERT，不用大模型？
分诊是高频、简单、单薄的判断 —— 小模型毫秒级、几乎零成本就能干好；大模型又贵又慢，让它干这个是杀鸡用牛刀。工程铁律：能力匹配就好，别为小事请专家。同理 BM25 能挡住的问题也别动用向量检索。
BM25 和向量检索不是重复了吗？留一个不行吗？
不重复，它们性格互补：BM25 认词不认义（换个说法就查不到，但极快极便宜），向量认义不认词（改写也能中，但每条都要算向量）。缓存层用 BM25 是因为 FAQ 场景「来问的人措辞高度相似」，关键词命中率高；长尾问题才交给向量 + 重排。
Redis 已经能挡住高频问题，为什么还要 BM25 + MySQL？
Redis 只有「一模一样才命中」，措辞差一个字就漏过去。BM25 + MySQL 住的正是「几乎一样」的那一层 —— 问法和预置答案差几个字，仍能命中 FAQ 免走 RAG。三层各挡一个相似度区间，缺一层漏斗就少一级。
回答已经能生成了，为什么还要专门的评估体系？
因为「感觉变好了」不是证据。改了切块大小、换了检索策略、调了提示词 —— 每次改动都要在同一套 QA 集上重跑 RAGAS 对比分数，才能确认是改进还是退步。评估的意义不是打分本身，而是让迭代可自动化、可回滚。
LangChain 和 LangGraph 什么关系？我该学哪个？
同一个团队的两代编排思路：LangChain 把步骤串成链（有向无环，一条道走到黑），LangGraph 把步骤连成图（支持循环、分支、并行、人工介入）。简单任务链够用；流程一旦要「看情况回头」（比如水没开接着烧），就必须上图。两者共用组件生态，学过链再上图很顺。
LangGraph 里没有 while 循环，那循环怎么写？
循环 = 「条件边指回自己」：条件函数看状态返回「水没开」，路由表把「水没开」映射回烧水节点自己 —— 图里有环，执行就会转圈，直到条件放行。这也是它和 Chain 最本质的区别：Chain 的图无环，想回头都不行。
为什么不把所有文档直接塞给大模型，还要搞这么一套？
三个理由，个个都硬：① 付不起——每次问答都要把全部教材重传一遍，按 token 计费，教材越多越烧钱；② 太慢——用户要的是 2 秒不是 2 分钟；③ 反而更不准——资料全堆进去，模型会「迷失在中间」（lost in the middle），中间那段经常被无视。RAG 的做法是每次只翻最相关的几页：便宜、快、还更准。
为什么不用 MySQL 的 LIKE 直接查关键词，要专门搞向量库？
LIKE 是 Ctrl+F：字面一模一样才查得到，「怎么保养车」永远查不到「汽车维护技巧」。Milvus 吃向量、按意思找。而且本系统其实两头都用了：稀疏向量 / BM25 管字面，稠密向量管语义——「混合检索」就是承认各有盲区、两路互补。
token 和温度到底是什么？老是记不住。
token 是模型眼里的「字」——计费单位、也是输出的最小单位，所以「逐 token」就是「每写出一小截就推给你」；温度是发挥旋钮——低温稳定、高温发散。专门讲过一遍：第⓪章 · 大模型三常识，忘了就回去扫一眼。
整条链路的自检顺序：① print(len(documents)) 有货 → ② print(len(chunks)) 且子块带 parent_id → ③ Milvus 行数对得上且重复入库不重复计数 → ④ 相关问题能召回正确父块、无关问题分数明显偏低。四关都过，存储与检索就算验收，可以进入「生成」环节。
